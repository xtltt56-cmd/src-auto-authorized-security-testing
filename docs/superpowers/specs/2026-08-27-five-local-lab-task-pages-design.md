# 五个本地靶场独立任务页设计

## 背景

当前“本地靶场”页面可以显示 Juice Shop、DVWA、WebGoat、VAmPI 和 Business API 五个回环靶场，但表格行本身不可点击，页面上的“打开当前任务”和“打开任务详情”都固定进入同一个聚合任务 `run-local-001`。这无法满足“点击每个靶场，查看对应任务页面”的使用要求，也容易让用户误以为五行状态都来自同一个任务。

## 目标

- 五个靶场分别拥有稳定、唯一的本地任务 ID、任务状态、阶段、计数和脱敏事件。
- 桌面端可以点击靶场名称或该行的“查看任务”按钮进入对应详情。
- 移动端使用可点击卡片展示五个靶场，避免依赖横向滚动表格。
- 详情页复用现有任务详情组件，并准确显示靶场名称、`127.0.0.1` 端口、数据来源和回环网络边界。
- 聚合任务入口继续保留，用于查看完整五靶场回归。
- 没有报告的靶场明确显示“当前尚未生成报告”，不跳转到不相关报告。
- 所有浏览器验收只允许访问 `127.0.0.1`，不得访问真实目标或调用远程 AI。

## 非目标

- 不在本次改造中新增漏洞扫描器或攻击载荷。
- 不改变补天目标的授权、人工确认和最终人工提交边界。
- 不把前端夹具状态描述为真实容器扫描成绩。
- 不在浏览器中直接打开或操作靶场应用本身。
- 不新增前端框架、状态管理库或路由依赖。

## 方案选择

采用“一个通用任务详情模板 + 五套独立任务数据”。`TaskDetailPage` 继续承担通用任务展示，`LabStatus` 通过 `taskId` 关联到对应的 `TaskSummary` 和 `TaskEvent`。这样可以复用已经通过测试的暂停、恢复、停止、阶段轨道、事件明细和报告入口，避免维护五个重复页面。

未采用的方案：

- 表格行内展开：移动端信息密度过高，也不符合独立任务页要求。
- 五个静态页面：重复代码多，后续状态和安全边界容易不一致。

## 用户流程

1. 用户从总览进入“本地靶场”。
2. 页面继续显示“五靶场总任务”入口。
3. 用户点击某个靶场名称或该行的“查看任务”按钮。
4. 应用根据 `LabStatus.taskId` 打开该靶场独立任务详情。
5. 详情页显示靶场名称、回环端口、状态、阶段、进度、计数、事件和报告状态。
6. 用户点击“返回靶场列表”回到五靶场矩阵。
7. 用户可以继续打开另一个靶场，且不得残留上一个靶场的标题、端口、事件或报告状态。

## 桌面端设计

保留当前矩阵表格。每行提供两个等价入口：

- 靶场名称使用语义化按钮，视觉上保持文本链接样式。
- 最后一列显示“查看任务”按钮和箭头图标。

按钮的无障碍名称包含靶场名称，例如“查看 Juice Shop 任务”。键盘用户可以用 Tab 聚焦并按 Enter 打开。行本身不绑定点击事件，避免可点击表格行产生语义和焦点问题。

## 移动端设计

在窄屏下将表格行转换为独立卡片，每张卡片显示：

- 靶场名称和 `127.0.0.1:<端口>`。
- 健康状态和当前阶段。
- 耗时和候选数量。
- 占满卡片宽度的“查看任务”按钮。

卡片顺序与桌面端表格一致，不隐藏任何靶场。

## 数据模型

`LabStatus` 新增必填字段：

```ts
taskId: string
```

五个映射关系固定为：

| 靶场 | 任务 ID |
|---|---|
| Juice Shop | `run-lab-juice-shop` |
| DVWA | `run-lab-dvwa` |
| WebGoat | `run-lab-webgoat` |
| VAmPI | `run-lab-vampi` |
| Business API | `run-lab-business-api` |

聚合任务 `run-local-001` 保持不变。每个独立任务都使用 `kind: 'local-lab'` 和 `networkContact: 'loopback'`，并至少拥有一条明确对应本靶场的脱敏事件。

前端数据仍标记为 `source: 'local-fixture'`。真实容器是否可达通过独立的本机端口验收检查证明，不由前端夹具数字代替。

## 组件和状态流

### `LabMatrix`

- 将 `onOpenTask?: () => void` 改为 `onOpenLabTask: (taskId: string) => void`。
- 每个靶场按钮调用 `onOpenLabTask(lab.taskId)`。
- 聚合任务入口不再由 `LabMatrix` 负责，继续保留在 `LabsPage` 顶部横幅中。

### `LabsPage`

- 顶部“打开当前任务”继续打开 `run-local-001`。
- 将 `onOpenTask` 直接传递给 `LabMatrix`，用于打开五个独立任务。

### `App`

- 继续使用 `selectedTaskId` 选择任务。
- 根据当前任务 ID 从 `snapshot.labs` 派生对应的 `selectedLab`，不新增重复状态。
- 将 `selectedLab` 传给 `TaskDetailPage`。
- 返回操作清除 `selectedTaskId`，回到当前“本地靶场”导航。

### `TaskDetailPage`

- 新增可选的 `lab` 属性。
- 有 `lab` 时显示 `127.0.0.1:<端口>`、靶场健康状态和“本地夹具”数据来源。
- 没有 `lab` 时继续显示五靶场聚合任务摘要。
- `lab.reportId` 存在时允许进入候选与报告页面；不存在时点击“查看报告”显示“当前靶场尚未生成报告”的本地提示。
- Business API 的“API 对象对比”加入阶段轨道，避免回退到按百分比猜测阶段。

## 错误与边界处理

- `taskId` 必须能在 `snapshot.tasks` 中找到；单元测试覆盖所有五个映射。
- 某靶场没有报告时，不得打开其他靶场报告。
- 切换靶场后，任务详情状态由新的 `task.id` 初始化，不沿用前一个任务的暂停或取消状态。
- 页面继续显示“网络接触：仅回环”和“远程 AI：已禁用”。
- 浏览器测试记录所有请求，主机名不是 `127.0.0.1` 时立即失败。

## 测试设计

### 组件与集成测试

- 五个靶场名称和五个独立“查看任务”按钮全部存在。
- 逐个点击按钮时，回调收到对应的唯一任务 ID。
- 从应用层打开每个任务，标题和端口与靶场一致。
- 返回列表后可以继续打开下一个靶场。
- 无报告靶场显示本地提示，有报告靶场可以进入报告区域。

### 浏览器测试

- 桌面端循环点击五个靶场，验证名称、端口、阶段和返回路径。
- 手机端验证五个卡片入口可见且没有横向溢出。
- 验证页面标题、非空渲染、无框架错误覆盖层、控制台无应用错误。
- 验证测试过程中外部请求数量为零。

### 本地靶场运行检查

仅对以下回环地址执行轻量健康检查：

- `127.0.0.1:3000`
- `127.0.0.1:8081`
- `127.0.0.1:8082`
- `127.0.0.1:8083`
- `127.0.0.1:8084`

验收报告必须分别列出“前端可视化交互结果”和“本地端口实机可达结果”，不得把两者合并成一个通过结论。

## 完成标准

- 五个独立入口均可通过鼠标和键盘打开正确任务。
- 五个详情页的数据不会串台。
- 聚合任务入口仍然正常。
- 桌面端和手机端均无明显裁切、重叠或横向滚动陷阱。
- 前端单元测试、构建、lint、Storybook 和 Chromium E2E 全部通过。
- 浏览器控制台无应用错误，外部请求为零。
- 五个本地端口的实机可达结果逐项记录；不可达时如实报告，不伪造为通过。
