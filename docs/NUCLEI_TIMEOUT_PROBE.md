# nuclei 全模板扫描超时实测与分批实施记录

**日期：** 2026-11-20（Asia/Shanghai）
**范围：** 仅五个固定回环靶场；不触碰真实外部目标。
**当前结论：** A 方案已落地为“真实模板 ID + 请求预算分批 + 逐批入库合并”。早期“4 批均分”只是实施前估算，真实目录数据确定为 **5 批**。

## 最终实施口径

- 通过 pinned nuclei 自身的 `-tl -td -nc` 输出解析真实 `id` 与 `metadata.max-request`，不把文件名片段冒充模板 ID。
- exposure 目录共 **1510 个模板**，ID 全部合法且唯一；56 个模板未声明 `max-request`，按 3 请求保守估计。已声明请求合计 3948，加缺失估值后总预算为 **4116**。
- 每批预算约 1000 请求，多目标时按目标数等比收缩；直接 `-id` 参数最多 2000 个 ID、12000 字符。
- 真实切片为 **5 批**：模板数 `[313, 1, 389, 578, 229]`，请求估计 `[605, 1305, 999, 767, 440]`，ID 字符串长度 `[5057, 16, 7581, 11991, 5394]`。
- `zip-backup-files` 声明 1305 请求，保持单模板 singleton；不拆改签名模板，不提高限速、并发或 600 秒上限。
- 每个完成批立即沿用现有 ingest 与 fingerprint 去重路径；后批失败保留此前已入库结果并返回 `partial_tools`。多模板批超时先记录 split，再二分重跑；父批部分输出不入库。
- 普通非 nuclei 适配器及既有 fake adapter 行为不变。

## 实施前测量

| 实验 | 实测结果 | 解释边界 |
|---|---|---|
| 模板加载固定成本 | 约 25–37 秒/容器 | 不是只由下载造成 |
| 模板卷热缓存 | 37.58 秒，仅比冷启少约 2.6 秒 | 收益不足且增加卷可信面，未采用 |
| 150 个 exposure 模板 `-id` 切片 | 203 请求；扫描 92 秒；总计 119.49 秒 | 证明小批可完成，不代表全量耗时 |
| exposure 早期采样 | 约 3784 请求、推算约 1892 秒 | 已被最终目录元数据口径取代，不作为最终批次预算 |
| `zip-backup-files` 单模板 | 容器启动后 633 秒仍为 running，随后收拢 | 宿主任务曾被工具时限中止；没有有效扫描耗时或完成率结论，不能承诺其 600 秒内完成 |

因此，分批解决了“把可完成的小批分别执行并持久化”的编排问题，但不保证所有重型单模板都能在固定窗口内完成。超窗 singleton 仍应明确返回 `partial_tools`。

## 实机发现并修复的初始化缺陷

首次真实小批扫描连续出现 `no templates provided`：新容器在使用 `-id` 前未可靠完成模板安装。单独添加 `-ut` 实测会在更新后退出，不能直接当作扫描参数。

最终 runner 在同一容器内执行固定初始化程序：先 `nuclei -ut -nc`，再执行不携带目标的 `nuclei -tl -nc` 就绪校验，最后 `exec nuclei "$@"`。目标 URL、模板 ID 和其他审阅参数只作为位置参数传递，不插入 shell 程序字符串；不使用模板卷，不新增用户可控 shell/路径参数。更新、校验和扫描共享同一个 600 秒 deadline。

该修复先用失败回归证明旧 create argv 缺少初始化与就绪校验，再实现并通过 `NucleiRunnerTests + NucleiBatchTests` 共 19 项定向测试。目录解码另修复了默认 1 MiB 上限导致的静默截断：现在先限制原始目录总字节数，再在 64 MiB 内完整 UTF-8 解码；超过 1 MiB 的目录有独立回归。

## 五靶场本轮 L4 小批证据

统一使用真实 CLI/ingest 链、confirmed loopback scope、人工计划、`--execute-live`、pinned nuclei、`swagger-api` 单模板和独立验证数据库。所有运行均保持 `-rl 2 -c 1 -bs 1`，ScopeGuard 越界入库为 0。

| 靶场 | 回环入口 | 最终结果 | 入库候选 |
|---|---|---|---|
| Juice Shop | `127.0.0.1:3000` | `completed_tools` | 1（Swagger API，info） |
| DVWA | `127.0.0.1:8081/login.php` | `completed_tools` | 0 |
| WebGoat | `127.0.0.1:8082/WebGoat` | `completed_tools` | 0 |

Juice Shop 的首次失败保留在验证目录，最终成功 run_id 为 `527f75b2de2f4b79a78771439c3ecda5`；DVWA 最终成功 run_id 为 `96a1755fdc564f98b561fd6b4c815a91`。其余成功 run_id 分别为 WebGoat `cbbeab849b564b0ea566a60769789513`、VAmPI `3024a1bf47ba4505a115f5d1c1642e5e`、Business API `30b5864b05bd477786de001391aa5a5b`。

这证明五个靶场均能完成**本轮小批 nuclei 出站与入库链**。零候选表示该模板未命中，不是扫描失败，也不证明靶场没有漏洞。它不表示五个靶场都已完成 exposure 全量五批扫描，也不替代固定只读配方/DeepSeek Agent 验收。

## 验证与未验收项

- A 方案新增 `NucleiBatchTests` 10 项；初次 8 项在旧实现上出现 7 errors + 1 failure，实现后转绿，之后扩展目录大小与多目标预算用例。
- 真实目录集成曾只解析到 666 个模板并错误生成 3 批；修复后完整解析 1510 个并生成 5 批。
- 本轮未调用 DeepSeek 或其他付费 API。五靶场固定配方/DeepSeek Agent 复测列入外部测试清单，不能在发布材料中记为已通过。
- 全量双版本回归、覆盖率、前端检查、敏感信息门禁及最终环境收拢以 `RELEASE_MANIFEST.md` 和发布交接记录为准。

## 明确不采用

- 不使用模板卷缓存，不单纯提高 600 秒超时，不提高 `-rl/-c/-bs`。
- 不通过文件名猜真实模板 ID，不解析带 ANSI 颜色的目录正文，不复用默认 1 MiB 工具输出解码来读取完整目录。
- 不为了消除 `partial_tools` 而丢弃失败状态、放宽 ScopeGuard 或声称 100% 模板覆盖。
